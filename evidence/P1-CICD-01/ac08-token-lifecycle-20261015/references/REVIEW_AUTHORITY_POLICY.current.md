# 코드 병합·증적 저장소 독립 리뷰와 Lead 위임 정책

결정일: 2026-09-18 KST. 근거: 프로젝트 사용자 이권욱의 지시 — “코드 병합 절차만 독립 리뷰절차를 거치고 그 외 절차는 리드에게 일임”.

추가 확인: 같은 날 사용자가 “증적 저장소는 독립 리뷰가 맞음”이라고 명시했다. 따라서 `fds-project-evidence`는 코드 외 변경도 독립 리뷰를 유지하는 예외다.

2026-09-23 개정: 프로젝트 중간 결과 회고에 따른 사용자 정책 변경 안내(“코드 리뷰 및 배포 절차 간소화”)에 따라 사전 검증(Pre-check)용 코드는 별도 코드 리뷰 없이 담당 Lead 권한으로 즉시 병합할 수 있고, 해당 코드를 실제 운영(Production) 서버에 Runtime으로 적용하는 시점부터는 코드 리뷰가 필수다. 같은 날 추가 결정으로, 순수 검증기 역할에 한정된 Pre-check는 운영 서버에서도 리뷰 없이 실행할 수 있다. 상세는 §3.2다.

이 문서는 위 사용자 결정을 저장소에 기록하는 운영 정책 변경이다. 문서 PR의 병합·정본 패키지 발행 상태는 실제 GitHub 기록으로 구분한다. 정책 변경만으로 기존 티켓, Runtime 또는 Release가 완료되지는 않는다.

## 1. 적용 원칙

- **독립 리뷰는 코드 변경 병합과 `fds-project-evidence`의 PR에 필수다.** 단, §3.2의 사전 검증(Pre-check) 코드는 병합 시 독립 리뷰를 생략하고 운영 서버 Runtime 적용 전에 코드 리뷰를 받는다. 증적 저장소 예외를 제외한 코드 외 절차의 검토·실행 여부·결과 수용·인수·종결은 해당 업무의 Lead가 결정한다.
- Lead는 기존 책임 티켓/Decision/CR의 Lead다. 전체 업무를 한 명에게 재배정하거나 Support에게 새 승인권을 부여하지 않는다. 문서 정본과 Release는 정본 발행 담당 Lead가 결정한다.
- Support는 필요한 기술 지원·보안 및 타 영역 영향 확인에 참여한다. 코드 병합 및 증적 저장소 독립 검토 외 단계에서 Support의 별도 서명·승인 대기를 일률적 필수 조건으로 두지 않는다.
- 기존 Baseline §3.4·§17, Release/Ticket 정책, 개별 Runbook의 일반적인 “Support Review/독립 승인 후 실행·Done” 문구와 충돌하면 사람 간 승인 절차에 한해 이 정책을 우선한다. AC, 시험, 선행조건, 증적, 보안 통제는 유지한다.
- 과거 승인·리뷰·발행 이력과 불변 Tag/배포 묶음은 보존한다. 차기 정본에는 이 변경결정과 적용 범위를 동기화한다.
- 적용 대상 저장소(2026-09-23 사용자 확인): `fds-project-baseline`, `fds-project-evidence`, `fds-msa`, `infra-ansible`, `infra-cicd`, `infra-db`, `infra-dns`, `infra-harbor-trivy`, `infra-kubernetes`, `infra-lb`, `infra-monitoring`, `infra-pki`. 대상 외: `.github`(Organization public/private view 소개 페이지 게시용), `fds-project-architecture`, 보관 처리된 `fds-msa-legacy`, 개인 계정 저장소.

## 2. 코드와 문서의 구분

| 구분 | 예시 | 병합 판단 |
|---|---|---|
| 코드 변경 | 애플리케이션, 테스트, 스크립트, IaC/Ansible, Kubernetes manifest, CI/CD workflow, 의존성/lock, 인증서 profile, 실행 시 소비되는 정책·설정 | 작성자 외 적격 검토자 최소 1인의 독립 리뷰 후 Lead가 병합 결정 |
| 일반 저장소의 문서·증적만 변경 (`fds-project-evidence` 제외) | 설명/계획/정책/Runbook, WBS, Release 기록, 원본 로그·hash·공개 지문 등 실행 입력이 아닌 기록 | Lead 검토 후 병합 가능. 작성자와 Lead가 같아도 별도 독립 승인 불필요 |
| 사전 검증(Pre-check) 코드 (§3.2) | 사전 검증 단계의 점검·수집·판정을 위해 작성된 스크립트·검증기와 그 시험 코드 | 별도 코드 리뷰 없이 담당 Lead 권한으로 즉시 병합 가능. 운영 서버 Runtime 적용 전 해당 SHA의 코드 리뷰 필수 |
| 혼합 변경 | 문서와 코드가 함께 포함된 PR | 코드 변경 기준 적용 |
| `fds-project-evidence`의 PR | 증적 편입·정정, 수신/인수 기록, 정책·양식 등 코드 포함 여부와 무관 | 최소 1인의 독립 리뷰 후 기존 증적 저장소 승인·병합 담당자가 판단 |

확장자나 PR 제목으로 분류하지 않고 실제 사용처와 diff를 확인한다. Markdown에 넣은 새 실행 로직을 실제 배포 입력으로 사용하는 경우, 자동화가 소비하는 JSON/YAML·Trust bundle·설정값, 실행형 웹 코드 변경은 코드 변경이다. 기존 명령의 설명이나 실행 결과 기록만 바뀌면 문서 변경이다. 운영 작업이라는 이름으로 미검토 코드 변경을 우회 적용하지 않는다.

## 3. 코드 병합 절차

1. 작성자는 책임 티켓/AC, 변경·영향·복구, 검증 결과·제한, 대상 HEAD를 PR에 기록한다.
2. 작성자 외 적격 검토자 1인 이상이 실제 diff와 관련 검증을 확인한다. 기존 역할 범위 내 대체 Reviewer를 사용할 수 있다. 작성자 자신의 검토와 AI 보조 점검은 타인의 독립 승인이 아니다.
3. Lead는 최신 HEAD, 독립 검토 근거, 해당 단계의 필수 검사 및 미해결 차단사항을 확인해 병합한다. 새 commit은 변경 부분과 영향 범위만 다시 검토하며 무관한 시험은 반복하지 않는다.
4. GitHub APPROVED, 기술 검토 의견, Reviewer 지정, 실제 Merge를 구분한다. 보호 기능이 제한돼도 정확한 SHA의 독립 검토 기록과 Lead의 수동 병합 판단을 보상 통제로 남긴다.

작업 브랜치·PR·수동 병합과 직접 main push 금지 원칙을 유지한다. CODEOWNERS에 이름이 있다는 사실만으로 독립 승인 완료를 주장하지 않는다. 증적 저장소 외의 문서 전용 PR은 Lead 결정 기록을 사용하며 작성자 자신의 GitHub APPROVE를 요구하지 않는다.

## 3.1 증적 저장소 예외

- `fds-project-evidence`는 [EVIDENCE_POLICY](https://github.com/321Team/fds-project-evidence/blob/b676375c8cb641b194db835f5df1b0671357a017/governance/EVIDENCE_POLICY.md)의 독립 검토·정확한 HEAD 확인·수동 병합 원칙을 유지한다. 문서나 로그만 포함됐다는 이유로 독립 검토를 생략하지 않는다.
- Lead의 자체 Runtime 판정과 증적 저장소 편입 심사는 구분한다. 작성자·실행자의 자체 검토만으로 독립 증적 검토를 완료했다고 표시하지 않는다. 기존 증적 저장소의 담당자·병합 책임을 새로 배정하지 않는다.
- 독립 검토는 원본 출처, 수신 바이트·해시, 실제 실행 여부, AC와 판정의 대응, 누락·오표기·민감정보, 정정 이유를 확인한다. 원본과 과거 승인 이력은 보존하고 정정은 새 기록으로 남긴다.
- 증적 PR의 독립 검토 완료만으로 별도 업무 티켓을 자동 Done 처리하지 않는다. 해당 Lead는 필수 AC·남은 작업을 근거로 종결을 판단한다.

## 3.2 사전 검증(Pre-check) 코드 예외 — 2026-09-23 개정

결정일: 2026-09-23 KST. 근거: 프로젝트 중간 결과 회고에 따른 사용자 정책 변경 안내 “코드 리뷰 및 배포 절차 간소화”.

| 단계 | 적용 기준 |
|---|---|
| Pre-check 코드 병합 | §3의 독립 코드 리뷰를 거치지 않는다. 책임 티켓의 담당 Lead가 자기 권한으로 즉시 병합할 수 있다. 작성자와 Lead가 같아도 된다. |
| 운영 서버의 순수 검증기 실행 | 아래 4-1의 순수 검증기 조건을 모두 충족하면 Runtime 적용으로 보지 않는다. 리뷰 없이 담당 Lead 판단으로 운영 서버에서 실행할 수 있다. |
| 운영(Production) 서버 Runtime 적용 | 적용 시점부터 코드 리뷰가 필수다. 적용할 정확한 SHA가 §3 절차의 독립 리뷰를 마치기 전에는 운영 서버에 적용하지 않는다. |

1. **대상.** 사전 검증 단계에서 대상 환경의 상태를 점검·수집·판정하려고 작성한 코드다. 예: preflight/precheck 점검·수집 스크립트, 검증기와 판정 도구, 그 단위·모의 시험 코드. 제목·라벨·확장자가 아닌 실제 사용처와 diff로 분류한다(§2).
2. **대상 외(§3 유지).** 아래는 Pre-check 코드로 분류하지 않는다.
   - Pre-check 코드와 운영 Runtime용 코드·manifest·IaC·배포 설정이 섞인 혼합 PR
   - 병합·Release 판정 게이트를 이루는 CI/CD workflow
   - 시크릿·무결성 검사기 등 보안 통제 코드
   - `fds-project-evidence`의 모든 PR(§3.1 유지)
3. **병합 기록.** 작업 브랜치·PR을 사용하고 main 직접 push·force push·자동 병합 금지는 유지한다. PR에는 `Pre-check` 분류와 책임 티켓, 병합 SHA, 담당 Lead, KST 시각을 남긴다. 상태는 `REVIEW=NOT PERFORMED (Pre-check)`로 표기한다. 이 병합을 코드 리뷰 완료, Runtime PASS, AC 인수로 표시하지 않는다.
4. **운영 Runtime 적용 시점.** Pre-check로 병합된 코드를 운영 서버에서 실행·설치·배포·영구 반영하거나 운영 배포 경로(CI/CD Delivery 등)에 편입하는 것을 Runtime 적용으로 본다. 운영 서버에서의 실행은 4-1의 순수 검증기 실행을 제외하고 Runtime 적용에 포함한다. 적용 전에 다음을 지킨다.
   - 적용할 SHA를 고정한다.
   - 직전 독립 리뷰 완료 SHA 이후의 전체 diff를 §3 절차로 독립 리뷰한다. 리뷰 이력이 없으면 적용 대상 코드 전체가 리뷰 범위다.
   - 리뷰에서 수정이 필요하면 수정 PR도 §3을 따른다.
   - Lead는 리뷰 완료 SHA와 적용 SHA의 일치를 확인하고 §4의 Runtime 기록에 함께 남긴다.
4-1. **순수 검증기 실행(운영 서버 완화).** Pre-check 코드가 순수 검증기 역할에 한정되면 운영 서버에서 리뷰 없이 실행할 수 있다. 판단은 담당 Lead가 한다. 순수 검증기 역할은 다음을 모두 충족해야 한다.
  1. 대상 서버의 설정·파일·패키지·서비스·방화벽/네트워크·데이터·계정/권한을 변경하지 않는다. 재시작·reload·캐시 초기화도 변경에 포함한다.
  2. 서버에 설치·상주하거나 cron/systemd 등에 등록하지 않는다. 1회 실행 후 종료한다.
  3. 결과는 실행자 작업 디렉터리나 지정된 수집 경로에만 남긴다. 그 결과를 운영 설정·배포 입력으로 소비하지 않는다.
  4. 이미 승인된 접근 계정·권한 범위 안에서 실행한다. 새 계정·권한·Secret을 만들거나 수집 자료를 승인 범위 밖으로 반출하지 않는다.
  5. 운영 가용성·성능에 영향을 줄 수 있는 점검은 제외한다. 예: 부하 시험, 장애 주입, 대량 조회·스캔.
   - 하나라도 벗어나거나 확인할 수 없으면 Runtime 적용이다(4 적용).
   - 실행 전 Lead는 코드가 위 조건을 벗어나는 명령(쓰기·재시작·설치·등록 등)을 포함하지 않는지 확인한다. 이 확인은 Lead 자체 확인이며 독립 코드 리뷰가 아니다.
   - 실행 기록에는 대상 서버, 실행 SHA, 명령, 계정, KST 시각, 순수 검증기 판단 근거, 결과 경로를 남긴다.
   - 결과는 사전 검증 판정이며 운영 적용·AC 인수로 표시하지 않는다.
5. **유지 통제.** 비밀키·Token·Password·Secret 커밋 금지, 필수 AC·시험·보안 기준, 운영 적용 시 선행조건·중단·복구 기준은 이 예외로 완화하지 않는다. 격리 환경의 후보 시험은 §4에 따라 Lead 판단으로 수행할 수 있다.
6. **적용 시점.** 이 개정이 main에 병합된 뒤 생성·갱신되는 Pre-check 코드 PR에 적용한다. 진행 중인 PR은 Lead가 Pre-check 분류를 PR에 기록하면 적용할 수 있다. 과거 리뷰·승인 이력은 보존한다.

## 4. Lead가 결정하는 절차

| 절차 | Lead의 판단과 남길 근거 |
|---|---|
| 문서·계획·Decision/CR·정본 후보 검토 | 해당 책임 범위의 결정, 변경 이유·영향, 관련 기록 및 필요 정합성 검증 |
| 운영 Runtime 실행, 배포, 영구 반영, 복구 | 검토·병합된 코드/설정의 SHA·Digest(Pre-check 병합 코드는 §3.2의 리뷰 완료 SHA), 대상·선행조건·성공/중단 기준·복구 방법, 실제 결과 |
| CA 발급·갱신·회수·Trust 적용 | 기존 CA/서비스 담당 범위, 승인 profile·자산·유효성·공개 지문, 실행/검증 결과. 개인키·Secret 비저장 유지 |
| 업무 결과 수용, AC 인수, Gate/Milestone 및 티켓 종결 | 필수 AC와 실제 원본 증적, 미실행·제한·잔여 작업, 해당 단계 판정. 증적 저장소 편입·정정 PR의 독립 검토는 §3.1에 따라 별도 유지 |
| 정본 최종화·Release 발행 | 문서 Lead 판단, 버전/Manifest/해시/필수 배포물 검증, 실제 병합·Tag·발행 결과 |

병합 전 정적 검사·단위/모의 시험·CI 및 필요한 격리 환경 시험은 후보 SHA와 시험 범위·격리/복구 조건을 기록하고 Lead 판단으로 수행할 수 있다. 이를 위해 코드 병합이나 독립 승인을 먼저 받도록 요구하지 않는다. 후보 시험 결과를 운영 배포·영구 반영 완료로 표시하지 않는다.

Lead가 직접 수행한 업무도 위임 범위 안에서 결과를 검토하고 인수할 수 있다. 동일 코드의 Runtime 실행·업무 결과 수용·Done마다 독립 Reviewer를 다시 기다리지 않는다. `fds-project-evidence`에 변경을 편입하는 PR은 §3.1에 따라 독립 검토한다. 단, 새 코드/실행 설정 변경이 필요하면 §3으로 돌아간다.

여러 단계의 판단은 한 티켓/PR의 한 기록에 함께 남길 수 있다. 단계별 결과만 구분하며 승인 문서나 PR을 단계마다 추가 생성할 필요는 없다. 다른 업무 영역의 산출물은 해당 Lead의 수신 조건과 연결하고, Support 협의를 새로운 상시 이중 승인 절차로 만들지 않는다.

## 5. 유지하는 통제와 기록

- AC·아키텍처·보안 기준의 실질적 변경은 해당 범위 Lead가 Decision/CR에 변경 이유·영향을 기록하고 정본에 인계한다. 단순 검사 실패를 승인 절차 간소화로 PASS 또는 AC 충족으로 바꾸지 않는다.
- STATIC / MOCK / CI / RUNTIME / REVIEW / MERGE / PUBLICATION은 별도 상태다. 코드 병합은 Runtime PASS가 아니며 CI 0건은 NOT RUN이다. SHA-256 일치는 무결성 확인이다.
- Lead 결정은 기존 기록에 `대상/단계 · Lead · KST 시각 · SHA/Digest(해당 시) · 검증/증적 · 판정/잔여 · 복구(해당 시)`를 남기면 된다. 적용되지 않는 항목의 별도 서류를 요구하지 않는다.
- GitHub 계정·조직/저장소 권한·Ruleset·Actions/Runner 접근은 이 문서로 변경되지 않는다. 정책 채택을 개별 서버 작업·배포·키 발급의 실제 수행 승인이나 완료로 기록하지 않는다.
- 2026-09-23 Pre-check 개정은 GitHub 계정·권한·Ruleset을 변경하지 않으며, 운영 서버 적용 전 코드 리뷰 의무를 면제하지 않는다.
- 본 변경 시점에 진행 중인 코드/혼합 PR은 독립 코드 리뷰를 유지한다. 증적 저장소 외의 문서 전용 PR과 코드 외 업무는 Lead 위임 기준을 적용한다. 증적 저장소 PR은 코드 포함 여부와 관계없이 독립 검토를 유지한다. 과거의 승인자를 새 판정의 승인자로 복제하지 않는다.
